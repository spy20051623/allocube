# 角色化界面语言

本系统的界面只展示用户完成当前任务需要的信息。数据库、接口并发控制和审计仍保留精确的开发术语，但这些字段不能直接泄漏到普通业务页面。

## 角色信息边界

| 角色或场景 | 应展示 | 仅供内部使用 |
|---|---|---|
| 注册与登录 | 用户名、姓名、工号、邮箱、验证码、密码要求 | UUID、验证码挑战 ID、标识占用规则 |
| 注册审核中 | 审核状态、修改原因、当前资料和可执行操作 | `applicationRevision`、会话和令牌清理 |
| 普通用户 | 当前工号、资料修改审核状态、有权机器、自己的占用 | 曾用工号、无权机器的资源组、连接信息、管理备注、占用批次和事务 |
| 机器管理员 | 被授权机器、资源配置、资源组、管理备注、成员、申请和维护影响 | 其他机器的管理备注、无关账号资料和用户 ID |
| 系统管理员 | 注册资料、工号、权限、最近提交时间和操作后果 | 页面中的并发版本号和原始状态枚举 |
| 审计与日志 | UUID、内部动作、原始状态、版本和错误上下文 | 不限制，但只在审计详情、日志或导出中出现 |

时间轴显示占用人的姓名和当前工号，不返回占用人的永久用户 ID。个人永久用户 ID 只放在“个人资料 → 支持信息”中，供排障时复制。

## 推荐用词

| 内部模型或旧用词 | 界面用词 |
|---|---|
| reservation / 预约 / 资源申请 | 占用 |
| reservation segment | 一条占用、占用时段 |
| batch / 原子提交 | 本次提交 |
| employee number | 工号 |
| initial employee number | 工号 |
| application revision | 最近提交时间；版本号不展示 |
| resource group version | 第 N 版配置 |
| utilization | 资源占用率 |
| resource pool | 资源配置、资源项 |
| allocation | 资源组成、分配数量 |
| reserved minutes | 占用时长 |

“申请”只用于需要人工审核的流程，例如注册申请和资料修改。统计区域必须在指标附近注明：占用率来自系统登记时段，不代表真实硬件使用情况。

## 标题与提示

- 页面标题和模块标题只负责命名，不重复解释页面或模块用途。
- 页面头和模块头不提供副标题插槽；新页面应复用统一标题组件。
- 业务页面不叠加英文眉题、中文标题和中文说明等多层标题。
- 可以从标题、字段或当前内容直接理解的信息不再额外提示。
- 必须保留的规则、权限范围和操作后果应靠近对应字段、数据、按钮或确认步骤。
- 状态结果、审核原因、错误反馈、通知正文和记录元数据属于业务正文，不作为副标题处理。
- 删除标题说明时必须同步调整标题栏高度、间距、对齐和空状态，不能只删除文字节点。

## 禁止直接展示

普通业务页面不得出现以下内容：

- 永久用户 ID、UUID（支持信息和审计除外）
- `PENDING`、`ACTIVE`、`DISABLED` 等原始枚举
- 申请版本、并发令牌、事务、原子改期
- 申请段、批次、整批回滚、配置版本号 `vN`

状态文案集中维护在 `src/ui-copy.ts`。新增状态时必须先补充中文映射和测试；未知状态显示“状态未知”或“其他系统操作”，不能回退显示原始枚举。

## 接口裁剪

- `/api/v1/auth/me` 不返回注册审批版本。
- `/api/v1/admin/users` 保留 `applicationRevision` 作为前端隐藏的并发令牌，同时返回 `lastSubmittedAt` 供页面显示。
- `/api/v1/users/directory` 仅向已启用用户返回正式账号的姓名、用户名、当前工号和账号状态，不返回邮箱、停用原因、最后登录、用户 ID、待审资料或申请信息。
- `/api/v1/timeline` 不返回占用人的用户 ID，也不返回资源组配置版本；只返回姓名、当前工号、是否本人和按权限裁剪后的占用详情。
- `/api/v1/machines/catalog` 只返回机器名称、资源总量摘要、标签、管理员名单和当前用户的权限状态；设备型资源只展示数量，不返回设备编号，也不返回地址、连接说明、资源组或管理备注。
- `managementNotes` 只能出现在经过机器管理权限校验的管理端响应中，不进入普通机器类型、时间轴、报表、导出、通知或审计正文。
- 机器统计中的用户排行不返回用户 ID，只返回姓名、当前工号和汇总数值。
- 报表和时间轴在读取时查询当前工号，因此资料修改通过后，既有占用也展示新工号。

## 代码评审检查

1. 新文案是否描述用户能完成的任务或操作后果。
2. 普通用户是否看到了管理员或开发者才需要的信息。
3. 原始状态是否经过集中映射。
4. “申请”是否只用于需要审核的流程。
5. API 是否返回了当前角色不需要的稳定 ID、版本或敏感详情。
6. 标题是否重复解释了自身含义，必要提示是否已经靠近其实际作用位置。
