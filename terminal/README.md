# Allocube 公钥同步终端

终端负责主动拉取平台个人公钥，并更新本机独立的受管公钥文件。没有网页、监听端口、用户登录流程或账户操作接口；不会创建、删除或迁移 Linux 账户，也不会修改本机密码、sudo 或 shell。部署时在本机确认 SSH 服务范围，后续同步可在该范围内自动接管新增账户；没有账户或配置变更时不改写 SSH 配置。

## 平台

个人资料页的“SSH 公钥”支持添加、导入 `.pub` 和删除公钥。最多 10 把，支持 Ed25519、RSA（2048–8192 位）和 ECDSA。仅保存公钥，增删前需要绑定邮箱的验证码，沿用平台会话与 CSRF 防护。验证码限定当前会话和具体操作，一次性消费；修改内容或账号状态后需重新验证。变更审计记录指纹与名称，不记录密码或公钥正文。

机器管理页的“公钥同步”生成有效期 10 分钟、一次性的接入凭据。机器本地生成 Ed25519 身份密钥，使用 private_key_jwt 兑换短期机器凭据；每次请求检查登记状态。重新登记或停用使旧机器凭据失效。平台通过当前机器成员/管理员权限限制可获取的公钥，并且只返回用户在针对该机器已激活的公钥。

平台需要可信 HTTPS；终端不再提供 HTTPS 服务，因此不需要终端证书、内部 CA 或回调地址。终端不会跳过平台证书校验；内部平台 CA 可以用 systemd 服务级别的 SSL_CERT_FILE 配置。

平台使用内部 CA 或验收自签证书时，将公开证书以只读文件提供给平台，并设置 `TERMINAL_CA_CERT_FILE`。接入命令会内嵌公开证书，下载使用 `--cacert`，登记使用 `--ca-file` 并将路径保存为终端配置的 `caFile`，后续定时同步自动使用同一证书。信任仅作用于这个终端的平台连接，不修改系统证书库。只接受公开 CERTIFICATE PEM，不能放入私钥。普通受信任 HTTPS 无需此设置。

数据库版本 25 增加机器公钥激活与操作验证码绑定表，升级保留个人公钥、账户、终端登记和审计。既有个人公钥需在公钥管理中明确选择机器激活，不自动扩展授权。旧终端操作 API 已移除。

## 两层管理

- 用户层：个人资料管理全部公钥。默认上传不激活机器；新增时可勾选“添加后自动激活所有可用机器”，平台按提交时的权限激活当前可用机器，与公钥创建在同一事务中完成，不影响以后新加入的机器。删除会取消这把公钥的全部机器激活。
- 机器激活层：个人资料的公钥列表中，每把公钥只提供“管理”按钮，弹窗内多选机器后批量保存，取消勾选即可停用；删除公钥入口也放在该弹窗内。机器管理页只配置同步服务接入，不放置个人设置。任何角色均只能修改自己的公钥激活。
- 停用一台机器的公钥不会删除个人公钥或影响其他机器；没有激活公钥时返回成功的空列表。
- 管理弹窗支持三态全选（未选、部分选中、全选）；搜索时全选只影响搜索结果，其余选择保留。
- 邮箱功能关闭则跳过验证；允许空邮箱时，有邮箱就验证、无邮箱跳过；禁止空邮箱但尚未绑定时，先绑定，再重新开始操作。邮件配置异常或发送失败不能当作关闭。
- 机器激活沿用当前 Allocube 会话，不再次要求个人公钥操作的邮箱验证码。两层都要求同源与 CSRF 检查。

## 本地映射

配置文件默认 `/etc/allocube-terminal/config.json`，只能由 root 修改：

```json
{
  "platform": "https://allocube.example.com",
  "terminalId": "平台生成的终端 ID",
  "identityKey": "/etc/allocube-terminal/identity.key",
  "stateDir": "/var/lib/allocube-terminal",
  "syncKeyDir": "/etc/allocube-terminal/synced_keys",
  "sshConfig": "/etc/ssh/sshd_config",
  "intervalSeconds": 300,
  "autoManageNewAccounts": true,
  "accountScope": "named",
  "userMapping": {
    "a12345678": "87654321",
    "developer": "12345678",
    "deploy": null
  },
  "disabledUsers": []
}
```

优先级：

1. root、所有 UID 0 账户、nobody 及 UID 65534/65535 强制排除，任何手动配置均不能覆盖。
2. `userMapping` 的值为 `null` 表示排除，优先于所有自动推导和旧版暂停配置；符合工号命名规则的账户也可以排除。空字符串不是排除，会报错。
3. `disabledUsers` 是旧版暂停同步功能，保留原有行为，不自动恢复 SSH 配置。
4. `userMapping` 中填写工号表示手动映射，覆盖自动推导，也可接管默认 UID 范围外的非保护账户。值无效则报错并跳过，不回退。
5. `accountScope: "named"` 为默认模式，仅自动选择“一位小写字母 + 合法工号”的账户。合法工号为 8 位数字或 wx 加 6–7 位数字。
6. 显式设置 `accountScope: "regular"` 时，自动选择 `/etc/login.defs` 的 `UID_MIN` 至 `UID_MAX` 范围内的本地账户；未配置时使用 1000–60000。不是无限制的 UID ≥ 1000。符合命名规则时推导工号，其余账户使用空公钥集合。无法推导工号不会猜测平台身份，但仍要求机器在线鉴权成功后才应用空集合。
7. 只读取本机 `/etc/passwd`，不扩展至 LDAP/AD 等目录账户；不存在的账户不会创建。

修改配置后先运行 `sudo allocube-terminal mappings` 查看范围，再运行 `sudo allocube-terminal configure-ssh` 确认并应用。例如，使用 `regular` 模式并配置 `"deploy": null`，会接管普通本地账户，但完整排除 deploy。

排除账户不下载或改写公钥，不修改密码、sudo、shell 或其他账户数据。若账户已经被接管，`configure-ssh` 会列出需要移除的 Allocube 专属 SSH 规则，确认后备份、移除并重载，恢复底层 SSH 策略。原先允许密码登录则恢复允许；原先禁止时不会强行开启。旧公钥文件及其他原有认证来源保留。日常同步不会自动移除排除账户的 SSH 规则，发现尚未移除的规则会提示运行 `configure-ssh`，不把暂停同步误报为已经恢复登录。仅将范围缩小或加入 `disabledUsers` 不会恢复先前的 SSH 规则；需要恢复的账户应明确设置为 `null`。

允许多个账户映射到同一个工号。工号唯一、不重用是平台维护约束；工号变更由管理员修改映射。开启自动接管后，同名账户的 UID 变化按新账户处理：先安全清空遗留的 Allocube 公钥，再按当前映射在线查询并接管；网络失败保持空公钥，下个周期重试。未开启时暂缓该账户，向平台求助。终端不记录额外的平台用户 ID 绑定。

## 安装

接入页面提供 `allocube-deploy-linux-amd64.tar.gz` / `allocube-deploy-linux-arm64.tar.gz` 下载。用户解压并进入目录后，复制页面命令执行；命令仅包含接入环境变量和 `bash ./install.sh`。包内包含固定安装脚本、对应架构的单文件程序和 SHA256SUMS。脚本负责校验程序及脚本摘要、身份登记、安装和 SSH 配置；非 root 用户运行时由脚本调用 sudo，保留所需接入变量。前端不拼接下载、解压、安装、systemd 或 SSH 操作逻辑。

部署入口环境变量：

| 变量 | 用途 |
| --- | --- |
| `ALLOCUBE_PLATFORM` | HTTPS 平台地址 |
| `ALLOCUBE_TERMINAL_ID` | 终端 ID |
| `ALLOCUBE_ENROLL_TOKEN` | 一次性接入令牌 |
| `ALLOCUBE_CA_CERT` | 可选的公开平台证书，Base64 编码 |
| `ALLOCUBE_CONFIGURE_SSH` | 默认 `ask`，本机确认 SSH 配置；`skip` 保留人工维护的配置 |

令牌不会写入 `.env`、服务配置或日志；脚本消费后移除环境变量，通过标准输入交给登记程序。使用本机安装锁防止并发部署。已有配置和密钥复用；登记失败保留状态，不盲目重试一次性令牌；同一终端已经登记成功时，通过现有身份密钥验证后可继续执行部署，不要求再次消费令牌。

部署依次完成安装、登记、映射展示、SSH 检查、定时器安装及首次同步。`configure-ssh` 对常规 SSH 配置准备账户专属规则，受管账户仅使用 Allocube 公钥文件并禁用密码与键盘交互认证。工号不存在、无权限及公钥空列表都是有效的空集合，照常写入并应用 SSH 配置；空集合意味着不能建立新的 SSH 登录。在 `/dev/tty` 中输入 `yes` 后重新校验、备份并重载；重载失败恢复原文件并尝试重新加载。重复执行保留其他账户规则，只移除明确排除的账户规则。root/UID 0 始终排除。

受管账户使用 `AuthorizedKeysFile <syncKeyDir>/%u`、`AuthorizedKeysCommand none` 和 `AuthenticationMethods publickey`，因此原有公钥文件及云平台公钥不再为这些账户提供 SSH 授权。原文件和全局云平台配置保留，root、UID 0 及未受管账户的配置不改变。旧版 Allocube 的多公钥来源配置块会在本机确认后升级到该规则。

服务检查枚举 systemd 管理的 OpenSSH 主进程，按正式 Id 去重（ssh.service / sshd.service 等别名只处理一次），不限制服务名称。读取真实可执行文件和命令行，保留 `-f`、`-p`、`-o` 等参数，并使用同一组参数校验候选配置；不删除运行参数来绕过冲突。共享配置写一次、各真实服务分别重载；不同配置一起预览、一次确认。旧 `sshConfig` 字段仍可读取，实际服务配置以运行参数为准，无需手填服务数组。

`sudo allocube-terminal check-ssh` 是离线预检：列出服务、配置路径、监听地址；临时候选文件检查后删除，不改动现有 SSH 配置、公钥或服务。预检通过后，`configure-ssh` 只在内存中拉取预览公钥；取消、预检失败或没有交互终端时，现有公钥文件也保持不变。

支持常规 `Match User` / `Match all`，在已有用户规则之前插入独立的 Allocube 块；通过 Include 引入的用户规则也保留。确认前逐账户比较未受管账户（含 root 和全部 UID 0）的有效配置。配置文件互相作为服务根配置引用、连接条件 Match、不能安全解析的包装脚本或参数、证书认证、自定义认证组合，会在写入前停止并指出服务/文件。运行中的 socket 激活服务保留关联关系；没有常驻 listener 或按连接启动 sshd -i 时给出具体处理方式，不猜测或关闭原服务。

SELinux 启用时（包括 permissive），预检要求专用公钥目录和目标公钥路径的持久标签类型为 `ssh_home_t`，已存在文件也须具有该标签；不再一律拒绝 enforcing。标签未就绪时，终端显示针对实际 `syncKeyDir` 的完整修复命令，持久规则和已有文件的重新标记均由管理员执行，不自动安装依赖、调用 `semanage` / `restorecon`、修改安全策略或关闭 SELinux。默认目录在 openEuler 24.03 LTS-SP3 上的首次配置命令：

```bash
# 仅缺少 semanage 时需要安装；dnf 按文件查找对应软件包。
sudo dnf install /usr/sbin/semanage
sudo semanage fcontext -a -t ssh_home_t '/etc/allocube-terminal/synced_keys(/.*)?'
sudo restorecon -Rv /etc/allocube-terminal/synced_keys
```

同一条规则已经存在时，先检查其用途，再决定是否用 `-m` 修改；不要直接重标记 `/etc`、主目录或身份私钥。旧版安装器会无条件拒绝 enforcing，须从接入页面下载新部署包，解压进入目录后执行 `sudo bash ./install.sh`，复用已登记身份。新建公钥在原子替换之前设置标签；后续替换保留已有完整上下文，SSH 配置及恢复操作也保留原标签。标签写入失败时保留原文件；标签或规则漂移时暂停新增授权，在可以保留原标签的前提下仍执行撤销。公钥内容及标签均未变化时不写文件。定制 SELinux 策略的额外限制仍需管理员根据审计日志处理；标签检查不等于真实 SSH 登录验收。

安装输出统一使用英文，默认只显示 SSH 变更确认和最终结果：账户数量、空密钥/暂停/无接管账户状态、配置路径及下一步命令。失败直接显示原因和继续方式，不要求向上翻日志。详细检查过程保存到 `/var/log/allocube-terminal-install.*.log`，权限 0600，结果中给出查看命令，不保存接入令牌。已登记机器在解压目录执行 `sudo bash ./install.sh`，使用现有配置和机器密钥在线验证后继续剩余部署，不需要接入环境变量或新令牌。

直接执行 `configure-ssh` 也默认显示简短结果，详细日志写入 `/var/log/allocube-terminal-ssh-*.log`。需要实时排查时使用 `sudo allocube-terminal --verbose configure-ssh`；`status` 查看简短账户/配置及 SSH 服务覆盖摘要，`mappings` 和 `check-ssh` 保留详细检查输出。

机器管理的“公钥同步 → 管理接入”中选择 x86_64 或 aarch64 并下载部署包，在目标机器解压、进入目录，再生成接入凭据并执行页面命令。安装脚本检查架构并校验 SHA-256，安装二进制、登记身份并安装同步定时器。接入凭据通过标准输入交给程序，有效期 10 分钟；复制的命令包含一次性凭据，不应转发。

重复接入使用 `setup`，保留已有身份密钥、用户映射、路径和暂停状态，只在登记成功后更新终端 ID。已有配置属于另一个平台时停止，要求管理员本地处理。部署包会检查 SSH 配置；常规配置经本机确认后应用，其他情况按下文人工处理。

平台已完成重新登记但响应丢失时，终端会用原身份私钥验证输入的新终端 ID，验证通过才保存新 ID。如果此时平台仍不可用，保留原配置；网络恢复后重复原接入命令即可核实已完成的登记，不会再次消费接入令牌。

Docker 镜像构建时编译并携带两种架构的程序。源码运行时先执行 `scripts/build-terminal.ps1` 生成 `terminal/dist`；未发布程序的架构无法生成接入命令。下载接口只分发公开部署包，不包含机器配置或身份私钥。平台升级导致部署包版本变化时，旧下载地址拒绝返回其他版本，应重新打开接入页面。

在 Linux amd64/arm64 构建：

```sh
CGO_ENABLED=0 go build -trimpath -ldflags='-s -w' -o allocube-terminal .
```

安装 root 所有的二进制后：

```sh
sudo allocube-terminal init
# 输入平台 HTTPS 地址、终端 ID 和一次性凭据。
# 管理员创建所需 Linux 账户，编辑映射和 SSH 配置。
sudo allocube-terminal mappings
sudo allocube-terminal configure-ssh
sudo allocube-terminal install
sudo allocube-terminal sync
```

install 只创建 root 所有的同步目录、systemd oneshot 服务和定时器，不修改 SSH 配置。升级时停止并禁用旧网页/broker socket，旧账户、公钥、sudo 和操作日志保留。

常规配置使用 `sudo allocube-terminal configure-ssh` 自动处理。需要自行维护时，受管账户的有效配置必须使用独立公钥文件，同时禁用密码和键盘交互认证。例如：

```text
Match User a12345678
    AuthorizedKeysFile /etc/allocube-terminal/synced_keys/%u
    AuthorizedKeysCommand none
    AuthenticationMethods publickey
    PasswordAuthentication no
    KbdInteractiveAuthentication no
Match all
```

这是受管账户的专属配置片段，必须结合本机现有配置检查优先级；其他账户的认证来源保持不变。修改后先执行 `sshd -t` 和 `sshd -T -C user=a12345678,host=localhost,addr=127.0.0.1`，确认有效配置，再由管理员重载对应 SSH 服务；保留团队 root 恢复入口。

终端每次同步会验证有效 SSH 配置仅使用同步路径、公钥认证，且禁用密码、键盘交互及外部公钥命令。仅支持 Match User / Match all；涉及地址、组等复杂 Match 条件或 SSH CA 时停止并要求手动处理。历史公钥文件不删除、不改写，但不再参与受管账户的 SSH 认证。平台公钥是这些账户的有效授权列表。

## 多服务变更与恢复

确认后先取得与同步共用的锁，再复查服务拓扑、账户、映射、Include 内容和最新公钥。等待人工输入时不占锁。新增空密钥风险、配置或账户变化会要求重新预览；不会拿旧确认直接处理新的影响范围。公钥按工号去重拉取，每个账户只有一份受管文件，与 SSH 服务数量无关。

变更以 `stateDir/ssh-operation.json` 记录阶段、每份配置的原文/候选和依赖快照，权限 0600；旧记录归档到 `ssh-history-*.json`。写入最新公钥后逐份原子替换配置，逐服务 reload，并等待监听就绪。多文件与多服务操作不是全局原子事务。失败时恢复原配置并重新加载；恢复不会写回旧公钥，避免重新授权已经撤销的密钥。

```sh
sudo allocube-terminal recover-ssh
```

只有一条未完成操作可存在，因此无需选择操作 ID。该命令读取阶段和当前实际状态，恢复之前校验全部配置与依赖；发现管理员在外部修改过文件时保留修改，指出冲突文件和日志位置，不覆盖。处理冲突后重复此命令即可继续。成功、已恢复、仍需恢复会分别输出明确状态。`status` 显示覆盖情况及需要执行的恢复命令。

成功配置后保存 `stateDir/ssh-inventory.json`，包含服务及配置摘要。每次原有定时同步检查覆盖范围，没有新增常驻进程或网络轮询。新服务、参数/配置变化、未完成操作或升级后尚无覆盖记录时，提示 `configure-ssh` / `recover-ssh`；对已绑定且 UID 未变化的账户，只应用旧集合与有效新集合的交集，继续撤销、暂缓新增授权。错误响应不会转为空列表。排除账户仍不写文件；未绑定账户不会在此状态下被接管。

已由管理员配置成完整 Allocube 策略的简单用户规则，可以经确认登记覆盖状态而不改写原文件。第一次升级需要在本机运行 `configure-ssh` 确认完整服务范围。已经确认且无配置变化时，重复运行不会要求确认或重复改写配置。

## 同步语义

- 每轮根据本机实际账户建立映射，按工号去重，最多每批 32 个工号。
- 每个 OK 响应必须明确包含完整 keys 数组，空数组清空相应受管文件；NOT_FOUND（工号不存在）和 DENIED（账号不可用或无机器权限）也作为空集合清空。平台为后二者显式返回 keys: []，终端兼容旧平台省略该字段的响应。
- 网络/TLS/机器鉴权请求失败、未知状态、缺失/重复响应、非法公钥不会被当成空数组；相应旧文件保留，输出原因。
- 单个工号的公钥无效、列表缺失或状态异常时，仅保留该工号的旧文件，其他工号继续更新（包括清除已撤销的密钥），整轮仍报告失败及对应工号。跨机器、缺失/重复工号等响应结构错误仍拒绝整个批次。
- 用户退出平台机器或被移除权限后，下次成功同步收到 DENIED 时清空公钥；不删除本地账户或文件，也不终止已有 SSH 会话。
- 公钥规范化、去重、排序后比较。仅顺序或重复次数变化不写文件；没有变化不触碰公钥文件的 inode、mtime 或权限，也不重载 SSH。
- 更新通过同目录临时文件和原子重命名完成；不跟随受管文件的符号链接。整轮同步使用 flock 串行执行。
- 日常同步不改 SSH 配置或历史公钥文件；由于受管账户只使用同步目录，空列表即可阻止新 SSH 登录。其他服务使用本机密码的行为不受影响。
- 写入前重新检查本地账户。原账户管理版本标记为 revoked 的账户不会自动恢复，管理员核实后处理旧 state.json 的撤销记录。
- disabledUsers / quiet 只是暂停同步，不等于撤销 SSH。要在本机撤销，请先暂停该账户同步，再清理其授权文件及管理员维护的其他来源，避免下一轮重新写回。

默认每轮结束后约 300 秒再运行，允许 60–86400 秒，加少量 systemd 抖动。修改间隔后重新运行 install。程序执行完即退出，没有常驻业务进程或主动监听。

定时同步默认使用 `SCHED_IDLE` CPU 调度策略和 idle I/O 优先级，优先让出 CPU 给普通任务；保留 `Nice=19`，但该值不影响 `SCHED_IDLE` 的调度。此设置不是 CPU 使用率上限，也不保证仅在空闲核心执行。更新程序后运行 `sudo allocube-terminal install` 可更新已有服务；手动直接运行 `sync` 不经过 systemd，继承调用者的调度策略。

```sh
sudo allocube-terminal quiet   # 持久暂停定时器，停止在运行的同步服务
sudo allocube-terminal resume  # 恢复定时器
sudo allocube-terminal rotate  # 本机发起身份密钥轮换
journalctl -u allocube-terminal-sync.service
```

quiet 后手动 sync 也不访问平台。已有公钥登录继续工作，新增或删除公钥延迟至恢复后的成功拉取。定时器仍会有周期唤醒，性能测试期间使用 quiet，不声称定时拉取绝对零开销。

平台属于 SSH 授权信任链：攻破平台并替换个人公钥可能授予机器访问权。出站拉取、HTTPS 和机器签名不隔离这一风险；团队 root 私钥继续在平台外保管。

## 验证

`go test` 包含手动映射覆盖、root/UID 0 排除、无效映射不回退、公钥集合比较、空集合、符号链接、限制选项、服务参数保留、覆盖变化只撤销、Match/Include 整合、并发锁及恢复冲突保护。两个固定名称的临时 systemd 服务可通过 `ALLOCUBE_TEST_SYSTEMD=1` 运行真实发现/重载测试；该测试只重载 allocube-multi-test-one.service 和 allocube-multi-test-two.service。Linux 文件所有权测试需要 root，仅在专用测试环境运行。

平台测试覆盖个人公钥所有权、邮箱验证策略和一次性凭据绑定、批量激活的权限及原子性、密钥格式、签名防重放、跨机器隔离、成员移除、明确空集合、旧操作入口移除、数据库升级及备份恢复。实际验收使用旧云服务器的独立 SSH 服务，不修改生产 SSH 登录端口。


## 自动接管与管理员求助

### 已安装终端升级

先更新主平台，再从接入页面下载对应架构的新版包，解压并进入目录，执行 `sudo bash ./install.sh`。同一入口自动识别首次安装与已有配置：首次安装需要页面生成的接入环境变量，升级不需要新令牌，也不改变原登记、映射及排除设置；`--resume` 保留为兼容别名。若旧服务存在但默认配置文件缺失，脚本停止并要求恢复配置，不覆盖原服务。确实需要重新登记时，使用新接入环境变量并显式执行 `bash ./install.sh --reenroll`。

安装器先验证包和原登记，然后停止定时触发，等待当前同步自然结束（最多 150 秒，不杀进程）。更新前在 `/var/backups/allocube-terminal/upgrade.*` 保存旧程序、默认配置目录和同步服务文件；备份仅 root 可访问，不代表整机或自定义外部目录的完整回滚快照。接着更新程序、检查 SSH、更新 systemd 配置、执行同步，成功后再启动定时器。SSH 变更继续使用其事务备份与恢复机制；已有 SSH 会话不主动断开。

失败输出直接显示原因和同一条重试命令。暂停升级期间的定时器保持停止，修复后再次执行安装脚本；原本处于 quiet 静默模式的终端升级后仍保持静默，不自动恢复同步。已有配置缺少 `autoManageNewAccounts` 时默认开启，显式 `false` 保持关闭。

新安装在本机 SSH 确认中明确授权后续自动接管，配置 `autoManageNewAccounts: true`。即使当前没有符合范围的用户，也可先确认 SSH 服务范围，后续新增用户自动接管。使用 `ALLOCUBE_CONFIGURE_SSH=skip` 的首次安装不启用自动接管。新旧配置缺少此字段时默认开启；管理员显式设置为 false 时保留关闭选择。升级由安装脚本自动更新服务配置，无需手动编辑此字段或额外执行 install。

每轮同步先检查账户；新账户及同名 UID 变化的账户遵循当前映射、范围和排除规则。root/UID 0 始终排除；历史执行器的撤销记录仍需管理员处理。明确无权限、工号不存在及空公钥列表是正常结果，不作为故障。首次接管沿用 SSH 配置预检、事务日志、备份和恢复；成功完成有效配置校验后才保存新账户绑定。批量新增只对每份变更配置写一次，每个受影响服务重载一次；正常同步不写配置、不重载。

定时服务仍使用 SCHED_IDLE 和 oneshot。除状态及公钥目录外，仅给已确认 SSH 根配置的专用父目录增加写权限，以支持原子替换；拒绝把 /、/etc、/root 等宽泛目录整体开放。新增 SSH 服务或现有配置变化仍需管理员在本机确认，不由平台下发配置。配置失败在同一条件下不会反复写入和重载；日志会提示本机运行 configure-ssh。未完成操作只自动尝试一次可核验的恢复，外部修改或恢复失败不强行覆盖。

终端只向 `/api/v1/terminal/machine/help` 发送需要管理员介入的求助，以及已报告问题的解除。正常同步、接管成功、空公钥列表不报告；网络故障按原同步周期本地重试，不增设心跳或失联通知。上报只包含事件 ID、修订号、固定错误码、账户/服务标识、处理结果和本机日志路径，不含密钥、配置正文、原始日志或用户全量列表。平台响应只有接收确认，不含命令或远程配置。

求助队列位于 `stateDir/help-requests.json`，最多 128 项，本机诊断位于 `stateDir/help.log`（内容有长度上限，仅 root 可读）。平台最多接受每次 16 项；已确认的相同问题不重复发送。响应丢失使用同一事件 ID 重试，问题解除后发送更高修订号并保留服务端终态防止旧请求重新打开。只在已确认本轮检查完成后解除问题；网络中断不会当作恢复。修改终端登记后旧登记的本地求助不向新登记重放。

平台保存回报并通知该机器的有效管理员；无人可接收时通知系统管理员。回报分 GENERAL（一般）和 URGENT（紧急）：恢复未完成需人工介入时为紧急，其余接管和配置问题为一般。旧终端缺少等级时按相同规则推导。一般回报只发站内通知；紧急回报的邮件还受平台邮件开关与管理员的管理通知偏好限制。重复回报不重复通知，由一般升级为紧急及问题解除各通知一次。机器管理页下方独立的“机器回报”列表只向管理员展示，待处理优先、紧急待处理靠前、已解决排后，分批展开历史。管理员可以手动标记已解决并记录操作者与时间；机器自动解除记录为机器确认，两者明确区分。同一已解决事件不会因延迟上报重新打开，终端恢复后再次出现的故障使用新事件。旧终端仍兼容，不发送新版回报，也不会触发“未上报”告警。

平台数据库增量升级至 27；上线顺序为先更新平台，再更新试点终端包。终端没有后台自动更新；下载新版包后通过同一个 install.sh 入口升级并更新服务配置。账户创建与下一轮扫描之间仍有空窗期；需即时接管可在创建后运行 `sudo allocube-terminal sync`。
